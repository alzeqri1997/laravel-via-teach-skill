2The hazard, stated plainly

LR-0002 predicted tenant isolation would be your main danger. Now we know the mechanism, and it is sharper than expected. From Ethaaf's own CLAUDE.md:

The single most important sentence in the codebase

TenantScope is a NO-OP when tenancy()->initialized is false. In central context — the Filament panel, a plain queue job, a console command — a query like Teacher::query() returns every tenant's rows.

Unpack what that means. There is one database. A mosque's students are not in a separate database; they are rows in a shared students table with a tenant_id column. A global scope silently appends WHERE tenant_id = … to your queries — but only when a tenant context is active. Outside that context, the same code returns everyone's data and raises no error.

Three rules follow. Treat them as non-negotiable until you understand the machinery:

Never call bare withoutGlobalScopes()

It strips TenantScope along with the actor scopes and silently returns every tenant's rows. If you must drop a scope, drop it by class name — the way NotificationService does.

Bulk insert() bypasses the tenant stamp

tenant_id is filled by a creating model hook. insert() skips Eloquent events entirely, so you must supply tenant_id by hand or write rows belonging to nobody.

Ask "what context am I in?" before every query

Inside an API request on a tenant route, the scope is live and you are safe. Inside a queue job, a command, or Filament, it may not be. $tenant->run(...) is what gives the scope a tenant to filter by — it is not a database switch.

You do not need to understand how the scope is installed yet. You need to be able to ask the question. A leak here is a data breach between mosques, not a bug report.

3Your real endpoint, traced

Here is a live, production endpoint: the association's student roster. Open these four files in your editor and follow along — this is the reading order from Lesson 2, applied for real.

① The route

routes/api/v1/association/students.php

Route::middleware('associationPermission:'.Permission::VIEW_STUDENTS)->group(function () {
    Route::get('/', [StudentController::class, 'index'])->name('index');
});

Mounted from protected.php with Route::prefix('students')->name('students.'), which itself sits under /api/v1/association behind auth:sanctum. So the real URL is:

GET /api/v1/tenant/association/students
This is why Lesson 2 insisted on route:list

That URL appears nowhere in a single file. It is assembled from three nested prefixes across two files. You will never find it by searching for the path string — you find it with php artisan route:list --path=association/students.

Note the middleware: not just auth:sanctum, but associationPermission:VIEW_STUDENTS. Being logged in is not enough; the caller must hold a specific permission. That is spatie/laravel-permission doing the work, and it is the authorization layer you will be expected to respect on every new endpoint.

② The controller

app/Http/Controllers/Api/V1/Association/StudentController.php

class StudentController extends Controller
{
    use ResolvesAssociation;

    public function __construct(protected StudentService $service) {}

    public function index(Request $request): JsonResponse
    {
        $students = $this->service->list($this->associationId($request));

        return $this->returnData(
            resourceResponse(AssociationStudentResource::collection($students)),
            __('association.students'),
        );
    }
}

Compare this to the textbook controller from Lesson 2. The shape is identical — thin, delegating — but three things are new and all three are Ethaaf conventions you must copy:

__construct(protected StudentService $service)

Constructor dependency injection. You never write new StudentService(). You declare what you need in the constructor and Laravel's service container builds it for you. The business logic lives in the Service, the database queries in the Repository, and the controller only wires HTTP to them. This is the service/repository pattern from CLAUDE.md, and it is the house style.

AssociationStudentResource::collection($students)

Exactly the Resource layer from Lesson 2 — ::collection() because this is a list, not one record. Your Lesson 2 knowledge transfers with zero adjustment.

$this->returnData(…, __('association.students'))

A project-specific response envelope, not Laravel. Ethaaf wraps every API response in a consistent structure with a translated message — __() is Laravel's translation helper, and this app is Arabic-facing. Copy this pattern; never return a bare Resource from a new endpoint, or your response shape will not match the rest of the API.

③ The service — where the tenancy nuance lives

app/Services/Association/StudentService.php

public function list(int $associationId): LengthAwarePaginator|Collection
{
    $repo = $this->repo
        ->forTenants($this->aggregator->tenantIds($associationId))
        ->withRelations($this->repo->listRelations());
    // …
}

Read the docblock the team wrote above that method — it is the most instructive comment in the file:

From the code's own documentation

"The association's مجمعات are resolved here and handed to the repository explicitly. Student carries Stancl's vendor tenant scope, which is dropped by the repository, so nothing else would constrain the query."

This is section 2's hazard, live in production code. The automatic tenant scope is deliberately dropped here, because an association legitimately spans several مجمعات and the vendor scope cannot express that. The isolation is then re-established by hand — forTenants(...) with an explicitly resolved tenant set.

That is the pattern to internalise: when the automatic guard is removed, something explicit must replace it. If you ever see a scope dropped with nothing taking its place, you have found a data leak — and that is a genuinely valuable thing to spot in review.

④ The resource

app/Http/Resources/Association/AssociationStudentResource.php

return [
    'id'           => $this->id,
    'student_name' => $this->contact?->name,
    'national_id'  => $this->national_id,
    'tenant_id'    => $this->tenant_id,
    'tenant_name'  => $this->tenant?->name,
    'mosque'       => $this->mosque?->name,
    'sections'     => $sections = $this->sectionsWithoutTerm->pluck('name')->unique()->values()->all(),
    // …
];

This is the JSON your SPA received. If you built a table against this endpoint, you have read this output many times — now you are looking at the file that produced it.

One piece of PHP worth naming, because it is everywhere in this codebase: ?-> is the nullsafe operator. $this->contact?->name means "if contact is null, evaluate to null instead of crashing." It is exactly JavaScript's ?. — you already know this one.

4The full trace

SPA:  GET /api/v1/tenant/association/students?per_page=20
        ↓
routes/api/v1/association/protected.php     prefix + auth:sanctum
        ↓
routes/api/v1/association/students.php      associationPermission:VIEW_STUDENTS
        ↓                                        ← no permission = 403
StudentController@index                     resolves association id
        ↓
StudentService::list()                      resolves the tenant SET explicitly
        ↓
AssociationStudentRepository                drops vendor scope, applies forTenants()
        ↓                                        ← THE isolation boundary
AssociationStudentResource::collection()    picks the columns
        ↓
returnData(...)                             Ethaaf's response envelope
        ↓
JSON → your table renders

Six layers rather than four. The extra two — Service and Repository — are Ethaaf's architecture, not Laravel's. Your reading order becomes: route → controller → service → repository → resource.

5Retrieval practice

In Ethaaf, how is one mosque's student data kept separate from another's?

You call bare withoutGlobalScopes() on a tenant model in Ethaaf. What happens?

You are adding a filtered student query to Ethaaf. Where does that logic belong?

From memory: why is a query in a queue job more dangerous in Ethaaf than the same query inside an API request?

Because TenantScope is a no-op when tenancy is not initialized. An API request on a tenant route initializes tenancy, so the scope appends WHERE tenant_id = … and you are protected automatically. A plain queue job, a console command or the Filament panel runs in central context — the same Student::query() returns every mosque's rows, silently and without error.

$tenant->run(...) is what supplies the tenant the scope needs. It is not a database switch — there is only one database.
