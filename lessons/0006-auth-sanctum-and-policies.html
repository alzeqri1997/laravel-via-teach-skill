Lesson 06 · Laravel 12

Who Are You, and May You?

Two different questions, two different mechanisms, two different status codes. Confusing them is the most common auth mistake — and a favourite interview probe.

Laravel 12 · ~30 minutes · Prerequisite: Lesson 5

The distinction the whole lesson rests on

Authentication asks "who are you?" — it is Sanctum, tokens, and the auth:sanctum middleware. Failure is 401.

Authorization asks "may you do this?" — it is policies and gates. Failure is 403.

If an interviewer asks you one thing about auth, it will be this. Being crisp about it signals you have shipped real APIs.

1Cold recall

From Lesson 5: name the five artisan commands for a new endpoint, in order. Then — which produces a 422, and why?

make:migration → make:model → make:request → make:controller --api → make:resource, then the route.

422 comes from the Form Request — specifically rules() failing. Laravel converts the validation exception into a 422 with an errors object automatically. Today you learn what produces the 401 and the 403 that sit next to it.

2Sanctum has two modes — know which you are in

This confuses almost everyone, because one package solves two different problems (docs):

ModeUsed byMechanism
API tokens Mobile apps, third parties, scripts Authorization: Bearer <token> header
SPA auth Your own first-party frontend Session cookies — no tokens at all
The thing most candidates get wrong

For your own SPA, Laravel's docs say plainly: "You should not use API tokens to authenticate your own first-party SPA. Instead, use Sanctum's built-in SPA authentication features." SPA mode uses cookies, which gives you CSRF protection and avoids storing a token in JavaScript where XSS can steal it.

Saying this in an interview — "cookies for first-party, tokens for third-party, and here's the XSS reason why" — puts you ahead of most candidates, who assume tokens are always the answer.

The same guard handles both. Sanctum checks for a session cookie first, then falls back to the Authorization header:

Route::get('/user', function (Request $request) {
    return $request->user();
})->middleware('auth:sanctum');

3Issuing a token

The login endpoint, essentially verbatim from the docs — this is a realistic take-home answer:

Route::post('/sanctum/token', function (Request $request) {
    $request->validate([
        'email'       => 'required|email',
        'password'    => 'required',
        'device_name' => 'required',
    ]);

    $user = User::where('email', $request->email)->first();

    if (! $user || ! Hash::check($request->password, $user->password)) {
        throw ValidationException::withMessages([
            'email' => ['The provided credentials are incorrect.'],
        ]);
    }

    return $user->createToken($request->device_name)->plainTextToken;
});
Hash::check($plain, $hashed)

Passwords are never compared directly or decrypted — they are hashed one-way and verified. Hash::check is also timing-safe. If you ever see $user->password === $request->password, that is a serious bug.

! $user || ! Hash::check(...)

Both failures give the same message. Deliberate: saying "no such email" tells an attacker which addresses are registered. Mention this in an interview — it shows security instinct beyond following a tutorial.

->plainTextToken

The only moment the plain token exists. Laravel stores a SHA-256 hash, so it cannot be recovered later — show it to the user once, or issue a new one.

Abilities, and revoking

// Scope a token to specific actions
$user->createToken('token-name', ['server:update'])->plainTextToken;

if ($user->tokenCan('server:update')) { /* … */ }

// Revoke
$user->tokens()->delete();                          // all of them
$request->user()->currentAccessToken()->delete();   // just this one (logout)

"How do you log out of a token-based API?" — delete the token. There is no session to destroy. That is the answer, and it is short.

4Authorization: policies

Authentication proved who you are. It said nothing about whether you may touch this particular record. That is a policy's job (docs):

php artisan make:policy ProgressPolicy --model=Progress
class ProgressPolicy
{
    public function view(User $user, Progress $progress): bool
    {
        return $user->id === $progress->student->teacher_id;
    }

    public function create(User $user): bool
    {
        return $user->role === 'teacher';
    }

    public function update(User $user, Progress $progress): bool
    {
        return $user->id === $progress->recorded_by;
    }
}

Note create() takes no model — there is no record yet. That asymmetry is a common interview follow-up.

Policies are auto-discovered: Progress → ProgressPolicy in app/Policies/, no registration needed. Three ways to invoke one:

// 1. In the controller — throws, becomes 403
Gate::authorize('update', $progress);

// 2. As a boolean
if ($request->user()->cannot('update', $progress)) { abort(403); }

// 3. On the route — before the controller runs
Route::put('/progress/{progress}', ...)->can('update', 'progress');

And the cleanest option, inside a Form Request — which is why Lesson 5's authorize() existed:

public function authorize(): bool
{
    return $this->user()->can('create', Progress::class);
}
Gates vs policies — a likely follow-up

Policies group rules around a model (can this user edit this post?). Gates are standalone closures for things with no model (can this user see the admin dashboard?). The docs' own analogy: "Think of gates and policies like routes and controllers."

5How Ethaaf does it

Your worked example uses a third layer — spatie/laravel-permission:

Route::middleware('associationPermission:'.Permission::VIEW_STUDENTS)->group(function () {
    Route::get('/', [StudentController::class, 'index']);
});

So Ethaaf stacks three checks: auth:sanctum (who are you), associationPermission (do you hold this named permission), and tenant scoping (which rows may you even see). Being able to describe a layered model like that — rather than "we check if the user is an admin" — is a strong signal in an interview.

Ethaaf also has a custom Rule::tenantExists('sections'), which is authorization expressed as validation: you cannot reference another tenant's record by guessing its id.

6Retrieval practice

What separates a 401 response from a 403 response?

Why do Laravel's docs say to use cookie-based auth, not tokens, for your own SPA?

Why does a policy's create() method differ from its update() method?

Out loud: "How would you secure an API endpoint so that a teacher can only edit progress records they created?" Speak it, then write it.

Layer 1 — authentication. auth:sanctum middleware on the route. No valid token or session → 401, before anything else runs.

Layer 2 — authorization. A ProgressPolicy::update() returning $user->id === $progress->recorded_by, invoked via Gate::authorize('update', $progress) or the Form Request's authorize(). Fails → 403.

Layer 3 — validation. Form Request rules() check the payload. Fails → 422.

Strong additions: route model binding gives you the 404 for free; and authorization belongs on the server regardless of what the UI hides, because the UI is advisory.

7Version shift

12 ← 10 · Ethaaf

Sanctum's concepts are identical, but Ethaaf runs Sanctum 3.x while Laravel 11+ requires Sanctum 4.x — a high-impact upgrade step where migrations must be published and the middleware config rewritten. Also: Laravel 10 had no php artisan install:api; Sanctum was installed manually.

12 → 13 · additions

Laravel 13 adds an #[Authorize] attribute you can place directly on a controller method, as shorthand for the can middleware. In 12, use Gate::authorize() or ->can() on the route.

8Your task before Lesson 7

One — secure the endpoint you built. In your practice app: add auth:sanctum, build the token-issuing route, and create a policy. Then prove all four codes with curl or Postman: 401 (no token), 403 (valid token, wrong user), 422 (bad payload), 201 (success). Seeing all four yourself is the point.

Two — out loud. Answer "what's the difference between authentication and authorization?" in under sixty seconds. Mention 401 vs 403 without hesitating.
