Lesson 09 · Laravel 12

Where Does the Code Go?

The service container, dependency injection, and the question senior interviewers actually use to separate juniors from mids.

Laravel 12 · ~30 minutes · Prerequisite: Lesson 8

The question this lesson answers

"You've got a controller that's getting long. What do you do?"

A junior says "split it into smaller methods." A mid-level developer talks about where responsibilities belong and when extra layers are worth their cost. The difference is not knowing more patterns — it is having a view on when not to use them.

1Cold recall

Spaced check, Lesson 5 and Lesson 6: what is $fillable protecting against, and what status code does a failed policy produce?

$fillable — mass assignment. Without it, create($request->all()) could let a caller set any column, including id or is_admin. It is an allow-list.

Failed policy → 403. (Failed authentication → 401; failed validation → 422.)

2The container, in one idea

You have been using it since Lesson 2 without naming it. Every time you typed this:

public function __construct(protected StudentService $service) {}

…you asked Laravel's service container for a StudentService, and it built one — along with anything that class needs, recursively. You never wrote new.

Bridge from frontend

It is Vue's provide/inject, or a React context, generalised to the whole application: ask for a thing by its type, get a configured instance, never construct it yourself. The gain is the same — the consumer does not know how its dependency was built, so it can be swapped in tests.

Two phrases interviewers like to hear:

TermMeans
Dependency injection A class receives what it needs instead of constructing it
Inversion of control The framework decides what to supply, not your class

Why it is worth anything: testability. If a controller calls new PaymentGateway() you cannot test it without charging a real card. If it receives one, a test can hand it a fake.

Binding an interface

The container's real power — in AppServiceProvider::register():

$this->app->bind(
    AssociationStudentRepositoryInterface::class,
    AssociationStudentRepository::class,
);

Now anything type-hinting the interface receives the concrete class. Swap the binding and every consumer changes at once — no edits anywhere else. This is exactly what Ethaaf does; its repositories are type-hinted as interfaces, which is why app/Repositories/Contracts/ exists.

3The layers, and what each is for

LayerResponsible forMust not
Controller HTTP in, HTTP out Contain business rules
Form Request Is this input acceptable? Touch the database beyond checks
Service Business decisions, orchestration Know about HTTP
Repository How data is fetched Make business decisions
Model What a thing is, its relationships Become a god object
Resource What the client sees Trigger queries (N+1)

The test for "does this belong in the service?" — would it still be true if this came from a CLI command instead of an HTTP request? If yes, it is business logic and belongs below the controller.

4Ethaaf, as the worked example

You traced this in Lesson 3; now you can read it architecturally:

// Controller — HTTP only
public function index(Request $request): JsonResponse
{
    $students = $this->service->list($this->associationId($request));

    return $this->returnData(
        resourceResponse(AssociationStudentResource::collection($students)),
        __('association.students'),
    );
}

// Service — the business decision
public function list(int $associationId): LengthAwarePaginator|Collection
{
    $repo = $this->repo
        ->forTenants($this->aggregator->tenantIds($associationId))
        ->withRelations($this->repo->listRelations());
    // paginated vs. full export decided here
}

// Repository — how the data is fetched
public function query(): QueryBuilder
{
    $this->withoutGlobalScopes([TermScope::class, StanclTenantScope::class]);
    return parent::query()->whereIn('tenant_id', $tenantIds ?: ['__none__']);
}

Three layers, three concerns. The controller knows nothing about tenancy; the service knows nothing about HTTP; the repository knows nothing about why these tenants. You can describe this in an interview as a system you have read and understood.

5When NOT to add layers

The answer that separates mid from junior

Asked "should every project use a service layer?", the impressive answer is no:

"For simple CRUD, a service that just forwards to the model is indirection without benefit — you read three files to understand one operation. Layers earn their place when logic is shared across entry points, when an operation spans several models, or when it is complex enough to test in isolation. Ethaaf needs them because tenancy and association-scoping are genuinely involved. A blog's post controller does not."

That answer shows judgement. Reciting "always use repositories" shows you read a blog post.

Honest trade-offs worth being able to name:

PatternBuys youCosts you
Service layerReuse across HTTP/CLI/queue; isolated testsMore files, more indirection
RepositorySwappable data source; queries in one placeOften wraps Eloquent, which is already an abstraction
InterfacesSwap implementations; fake in testsPointless with only one implementation
Fat modelsFewer files; logic near the dataGrows into a god object

6Retrieval practice

What does Laravel's service container do?

What is the main practical benefit of dependency injection?

Why might adding a service layer to simple CRUD be a mistake?

Out loud: "Your controller is 200 lines. Walk me through what you'd do." Answer as if to a senior engineer.

First, diagnose. Long because of validation? → Form Request. Because of query building? → scopes or a repository. Because of business rules? → a service. Because it is doing six unrelated things? → split the controller.

Then extract by responsibility, not by line count — the test being "would this still be true from a CLI command?"

Then say the mature part: you would not extract just because it is long. A 200-line controller doing one coherent thing with clear steps may be fine. The problem is mixed responsibilities, not size.

That final point is what makes the answer sound senior.

7Version shift

12 ← 10 · Ethaaf

The container is unchanged. What moved is where providers are registered: Laravel 10 lists them in config/app.php; 11+ uses bootstrap/providers.php, and new apps ship with just AppServiceProvider instead of five. Ethaaf has the older arrangement.

8Your task before Lesson 10

One — refactor on purpose. Take your practice endpoint and extract a service, binding an interface to it in AppServiceProvider. Then ask yourself whether it improved anything. For simple CRUD the honest answer may be no — and knowing that from experience is the point of the exercise.

Two — read Ethaaf's contracts. Open app/Repositories/Contracts/ and find where the interfaces are bound to concrete classes. Seeing a real interface binding is worth more than any explanation of one.

Three — out loud. "When would you use a service layer, and when wouldn't you?" Both halves. The second half is the one that scores.
