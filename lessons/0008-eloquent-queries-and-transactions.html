Querying Like You Mean It

Scopes, the retrieval methods and their failure modes, transactions, and the memory trap that kills exports. The query half of every take-home test.

Laravel 12 · ~30 minutes · Prerequisite: Lesson 7

1Cold recall

Two from earlier: (a) what does with('mosque') actually do at the SQL level, and (b) what are the four tests worth writing for a create endpoint?

(a) Two queries, not a join: one for the parents, then one WHERE id IN (…) for all related rows at once, matched up in PHP.

(b) Happy path (201 + assertDatabaseHas), unauthenticated (401), invalid payload (422), forbidden (403). Plus 404 for a missing record.

2Retrieval methods, and what they do when they fail

The failure behaviour is what interviewers probe, because it decides whether your controller needs a null check:

CallReturnsWhen nothing matches
::all()CollectionEmpty collection
::get()CollectionEmpty collection
::find($id)Model or nullnull
::findOrFail($id)ModelThrows → 404
::first()Model or nullnull
::firstOrFail()ModelThrows → 404
::firstOrCreate([...])ModelCreates it
::count() / sum() / max()A number0 or null
::exists()Booleanfalse
The OrFail habit

In an API, prefer findOrFail over find. The exception becomes a clean 404 automatically, so you skip the null check and cannot forget it. This is also exactly what route model binding does for you — now you know what it calls underneath.

3Building a query

$progress = Progress::query()
    ->where('pages', '>=', 5)
    ->whereBetween('recorded_on', [$start, $end])
    ->whereIn('student_id', $ids)
    ->whereNotNull('verified_at')
    ->whereHas('student', fn ($q) => $q->where('active', true))
    ->with('student')
    ->withCount('corrections')
    ->orderByDesc('recorded_on')
    ->paginate(20);

Three of these are worth singling out:

whereHas('student', fn ($q) => …)

Filter parents by a condition on their children — "progress belonging to active students". A frequent take-home requirement, and the thing people reach for raw SQL to do. whereDoesntHave() is the inverse.

paginate(20)

Returns a paginator and automatically adds meta and links to the JSON when wrapped in a Resource collection. Never hand-roll limit/offset for a list endpoint; use this and say so.

when($condition, fn ($q) => …)

Conditional clauses without breaking the chain:
->when($request->student_id, fn ($q, $id) => $q->where('student_id', $id))
This is how you build filtered list endpoints cleanly — a very common interview exercise.

4Scopes — naming a query once

A scope turns a repeated set of constraints into a name. Two syntaxes exist and you will meet both:

// Classic — the scope prefix. What Ethaaf and most existing code uses.
public function scopeVerified($query)
{
    return $query->whereNotNull('verified_at');
}

// Modern — the #[Scope] attribute, Laravel 12+.
#[Scope]
protected function verified(Builder $query): void
{
    $query->whereNotNull('verified_at');
}

Both are called the same way, and the prefix is dropped either way:

Progress::verified()->recentFirst()->get();
Local vs global — the distinction that matters

Local scopes are opt-in: nothing happens unless you call them. Global scopes apply automatically to every query on that model, which is how Ethaaf's tenant isolation works — TenantScope appends WHERE tenant_id = … invisibly.

That is the power and the danger together. Remove one with withoutGlobalScope(TenantScope::class) — by class name, never bare withoutGlobalScopes(), as Lesson 3 established.

5Transactions

When several writes must all succeed or all fail together:

use Illuminate\Support\Facades\DB;

DB::transaction(function () use ($request) {
    $progress = Progress::create($request->validated());

    $progress->student->increment('total_pages', $progress->pages);

    ActivityLog::create([
        'action'  => 'progress.recorded',
        'user_id' => auth()->id(),
    ]);
});

If any line throws, everything rolls back. Without this you could create the progress record, fail to update the total, and leave the data permanently inconsistent.

Interview question: when do you need a transaction?

Whenever one logical operation spans more than one write. Creating an order plus its line items. Transferring a balance. Recording progress and updating a running total. If a half-finished state would be wrong, wrap it.

A good extra: queue jobs dispatched inside a transaction can run before it commits and fail to find the row — Laravel's after_commit option exists for exactly that. Knowing this is a strong signal.

6The memory trap

This one shows up in real take-homes framed as "export all records":

// ✗ Loads every row into memory. 500k rows = out of memory.
foreach (Progress::all() as $row) { … }

// ✓ 500 at a time
Progress::chunk(500, function ($rows) {
    foreach ($rows as $row) { … }
});

// ✓ One at a time, lazily — reads like a normal foreach
foreach (Progress::lazy() as $row) { … }

// ✓ Chunk by id — safe when you are MODIFYING rows as you go
Progress::chunkById(500, function ($rows) { … });

chunkById matters: if you update rows while paginating with chunk, the offsets shift underneath you and records get skipped. Naming that unprompted is a senior-sounding detail.

Out loud: "Build me an endpoint listing students with more than 10 pages this month, newest first, paginated, filtered by section if provided." Say the query.

Progress::query()
    ->where('pages', '>', 10)
    ->whereBetween('recorded_on', [now()->startOfMonth(), now()->endOfMonth()])
    ->when($request->section_id, fn ($q, $id) => $q->where('section_id', $id))
    ->with('student')
    ->orderByDesc('recorded_on')
    ->paginate(20);

What earns extra credit: when() for the optional filter rather than an if, with('student') because the Resource will touch it (N+1), and paginate rather than get on a list endpoint.
