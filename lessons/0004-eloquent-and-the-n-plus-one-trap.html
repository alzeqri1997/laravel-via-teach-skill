Lesson 04 · Ethaaf

Relationships and the N+1 Trap

One innocent line in a loop can fire ten thousand queries. Ethaaf has this bug in production, documented and measured — today you learn to see it.

Laravel 10.50.2 · ~30 minutes · Prerequisite: Lesson 3

New in this lesson: version shifts

You asked to learn the 10 → 11+ differences along the way. From now on, grey sidebars like the one below mark places where Ethaaf's Laravel 10 differs from what newer docs, blog posts and AI answers will tell you. Ethaaf's version is always the default — the sidebars are reference, skippable on a first read, and never appear in the quizzes.

1Cold recall

Two from Lesson 3, from memory: (a) in what situation does Ethaaf's tenant scope silently stop protecting you, and (b) what must always replace a scope that has been deliberately dropped?

(a) When tenancy()->initialized is false — central context: the Filament panel, a plain queue job, a console command. TenantScope becomes a no-op and queries return every tenant's rows.

(b) An explicit constraint. In StudentService that was forTenants(...) with a resolved tenant set. A dropped scope with nothing replacing it is a data leak. Today you will see this exact pattern again, one layer deeper — and discover it has a second failure mode nobody warns you about.

2Relationships: the two you will meet most

From Ethaaf's Student model, the shapes you already saw in Lesson 2:

public function mosque()   { return $this->belongsTo(Mosque::class); }
public function sections() { return $this->belongsToMany(Section::class); }

The naming convention tells you which is which: singular means one (belongsTo), plural means many (hasMany, belongsToMany). Read the method name and you know the shape before reading the body.

Accessing one looks like a property, but is not:

You writeYou getWhat happens
$student->mosque A Mosque model Runs a query, then caches the result on the model
$student->mosque() A query builder Runs nothing yet — you can chain ->where(...)
The whole lesson in one sentence

Property access runs a database query. It looks like reading a field on an object — it looks free. It is not. Put it inside a loop over 500 students and you have just written 500 queries. That is the N+1 trap, and it is the single most common performance bug in every Laravel codebase on earth.

3N+1, as it actually appears

Lazy loading — one query per row, discovered one at a time:

$students = Student::all();              // 1 query

foreach ($students as $student) {
    echo $student->mosque->name;          // +1 query. Every. Single. Time.
}
// 500 students = 501 queries

Eager loading — tell Eloquent up front what you will need:

$students = Student::with('mosque')->get();   // 2 queries, total

foreach ($students as $student) {
    echo $student->mosque->name;              // already in memory. Free.
}

Two queries instead of 501. Eloquent fetches the students, collects their mosque_ids, and runs one WHERE id IN (…) to get every mosque at once (docs).

You have met this before

This is the same mistake as calling fetch() inside a .map() instead of requesting a list endpoint once. You already have the instinct — the difference is that on the frontend the network tab screams at you. Here there is no network tab. The queries are invisible unless you go looking, which is why this bug survives in production for years.

And the shape that causes it, straight from that report:

foreach ($mosques as $mosque) {
    $sectionsCount = Section::where('mosque_id', $mosque->id)->count();   // N+1
}

Note it is not even property access here — it is an explicit query inside a loop. Same disease. One query per mosque, where a single withCount would have done.

5How Ethaaf does it right

Now the good code — the repository behind the endpoint you traced in Lesson 3:

app/Repositories/Association/AssociationStudentRepository.php

public function listRelations(): array
{
    return [
        'contact' => $this->crossTenant(['id', 'contactable_id', 'contactable_type', 'name', 'phone']),
        'tenant',
        'mosque' => $this->crossTenant(['id', 'name']),
        'sectionsWithoutTerm' => $this->crossTenant(),
        'plan' => $this->crossTenant(),
    ];
}

That array is an eager-load manifest — every relation the roster's Resource will touch, declared up front so the page costs a fixed handful of queries no matter how many students are on it. Two refinements worth naming:

crossTenant(['id', 'name'])

Column pruning. The array selects only the columns actually needed. Less data over the wire, less memory. Note the comment in the real file explaining why 'tenant' is deliberately not pruned — Stancl stores name and manager as virtual attributes inside a data JSON column, so selecting id,name errors with "Unknown column". Pruning is not free; it requires knowing the model.

sectionsWithoutTerm, not sections

Student::sections() pins the pivot to the current term inside the relation definition. Across an association that term belongs to one مجمع, so the column came back empty for every other one. A relation can carry constraints you did not ask for — read the model before trusting a relation name.

6The twist: eager loading re-applies global scopes

Here is the part that connects today's lesson to Lesson 3's hazard, and it is genuinely subtle. From LoadsCrossTenantRelations:

From the code's own documentation

"Constraining the PARENT query to the association's مجمعات is not enough. Every eager-loaded relation runs as its own query and re-applies its own model's global scopes — including the tenant scope. … None of the roster's rows belong to it, so every relation came back empty: teachers with a null national_id, students with no mosque and no حلقة, on rows that plainly had them."

Read that symptom again, because it is how this bug announces itself in the wild: rows that plainly had data showing blank columns. Not an error, not a crash — just quietly empty fields. If a user ever reports that, this is now the first thing you check.

The mechanism: with('mosque') is not a SQL join. It is a second query against the Mosque model — and that second query re-applies TenantScope from scratch. The parent query being correctly scoped does nothing for it.

And the same discipline from Lesson 3 applies to the fix:

protected function crossTenant(array $columns = []): Closure
{
    return function ($query) use ($columns) {
        $query->withoutGlobalScopes([StanclTenantScope::class, TermScope::class]);
        // …
    };
}

Scopes removed by class name, never bare — exactly the rule from Reference 03. And the team wrote down why it is safe: "the relation is reached by foreign key from a row that has passed the association check, so it cannot pull in anything the caller was not entitled to see." The parent query is the authorisation boundary; the relations hang off it.

Fail closed

One more line from that repository, worth memorising as a principle:

return $query->whereIn(
    $this->model->getTable().'.tenant_id',
    $tenantIds ?: ['__none__'],       // ← fail closed
);

If the tenant list is somehow empty, the query matches the impossible value '__none__' and returns nothing. The team's comment: "An empty list must mean 'no students', never 'all of them'."

That is a security instinct worth stealing permanently. When a filter degenerates, it should degenerate toward showing nothing, never toward showing everything.

7Retrieval practice

Student::all() returns 500 students, then a loop reads $student->mosque->name on each. How many queries run?

Why did eager-loaded relations come back empty on Ethaaf's association roster?

Why does the repository pass ['__none__'] when the tenant list is empty?

A user reports that a column on a list screen is blank for most rows, though the data is definitely in the database. Name two different causes you now know of.

1. The eager-loaded relation re-applied a global scope. The relation query is its own query; TenantScope (or TermScope) filtered it down to nothing. Fix: drop those scopes by class name on the eager load, as crossTenant() does.

2. The relation itself carries a hidden constraint. Student::sections() pins to the current term inside the relation definition, so it resolves for one مجمع and is empty for the rest. Fix: use the unconstrained relation (sectionsWithoutTerm) and de-duplicate downstream.

A third, more mundane: the field was never added to the Resource (Lesson 2). Check that first — it is the cheapest to rule out.

8Version shift — Eloquent, 10 → 11+

Your first delta section. None of this changes what you write in Ethaaf today; it changes how you read documentation and other people's code.

10 → 11+ · casts

Ethaaf declares casts as a property: protected $casts = ['approved_at' => 'datetime']; — correct, and still supported in 11+.

Laravel 11 added a casts() method on the base model as an alternative. Newer tutorials show the method form. In Ethaaf, use the property. (upgrade notes)

10 → 11+ · lazy-load guard

Model::preventLazyLoading() exists in both 10 and 11+, so docs you find on it apply to Ethaaf unchanged. See the box below — your codebase already uses it. (10.x docs)

Ethaaf already guards against this — and that changes your job

In app/Providers/AppServiceProvider.php:

Model::preventLazyLoading(!app()->isProduction());

Model::handleLazyLoadingViolationUsing(function ($model, $relation) {
    if (isLocal()) {
        throw new LazyLoadingViolationException($model, $relation);
    }
    // …otherwise log it
});

So locally, an accidental lazy load throws an exception; outside production it is logged; in production it is allowed through so a missed relation cannot take the site down. This is a well-built safety net.

Two consequences for you. First, if you hit LazyLoadingViolationException, you have not broken anything — the guard is telling you exactly what this lesson is about, naming the model and the relation. Add that relation to the eager-load list and move on. Second, the 10,000-query paths in the report are mostly explicit queries inside loops, which this guard cannot catch. The net stops accidental lazy loads; it does not stop a deliberate Section::where(...) in a foreach. That is why reading the report still matters.

10 → 11 · migrations, if an upgrade ever happens

Two genuine hazards, both rated high impact. ->change() on a column now drops any modifier you do not re-state — an existing unsigned()->default(1) silently disappears unless repeated. And float/double column types were rewritten.

Not your problem today, but these are the two that bite hardest on a 10 → 11 upgrade. (upgrade guide)

Correcting something I told you earlier

I previously implied the restructured skeleton (bootstrap/app.php replacing app/Http/Kernel.php) was the main obstacle to upgrading. Having checked the official guide: it is opt-in. Laravel explicitly says "we do not recommend that Laravel 10 applications upgrading to Laravel 11 attempt to migrate their application structure" — 11 supports the 10 layout deliberately. The estimated upgrade time is 15 minutes. The real hazards are the migration changes above and Sanctum 3→4.

The practical consequence for you is unchanged: when 11+ docs describe bootstrap/app.php, Ethaaf will not have it. Look in app/Http/Kernel.php instead.
