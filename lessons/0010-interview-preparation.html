Saying What You Know

Nine lessons of knowledge. This one is about getting it out of your head and into someone else's — under pressure, in your second language, honestly.

~40 minutes · Prerequisite: Lesson 9 · Then: practice

What you actually have

It is easy to feel like a beginner because Laravel is new to you. Take an accurate inventory instead:

~4 years professional frontend (Vue, React, JS) — real engineering experience, not a bootcamp. You have consumed a production API for years, so you understand API design from the consumer side, which most backend juniors do not. You have read a sophisticated multi-tenant codebase — service/repository layers, global scopes, modular structure. You can build, secure and test an endpoint end to end.

You are not a junior backend developer who knows nothing. You are a mid-level developer moving across the stack. Those are different stories, and the second is true.

1Full-course retrieval

Everything, cold. This is the hardest recall in the course and the most valuable.

Without looking: name the status code and the mechanism for each — unauthenticated, forbidden, invalid data, missing record. Then explain N+1 and its fix.

401 — auth:sanctum, no valid token/session · 403 — policy or gate returned false · 422 — Form Request rules() failed · 404 — route model binding found no row

N+1: accessing a relationship as a property runs a query, so a loop over N rows runs N extra queries. Fix with with() to eager load (two queries total), or withCount() for counts. Model::preventLazyLoading() turns accidents into exceptions in development.

If that came out fluently, you can hold a Laravel conversation. If it did not, re-read References 02 and 04 — and note *where* you stalled, because that is your revision list.

2The ten questions

These account for most Laravel technical screens. Answer each aloud before reading on — reading an answer you have not attempted produces fluency, not retention.

1 · Walk me through the request lifecycle.

Entry point public/index.php → bootstrap → router → middleware → controller → model/database → response. Add: PHP boots fresh per request and dies after — which is why state lives in sessions, caches and the database.

2 · What is the N+1 problem?

As above. Add a real number: "I've read a performance report on a codebase where cascading N+1s produced over ten thousand queries in one call." Concrete beats theoretical.

3 · Authentication vs authorization?

Who you are versus what you may do. 401 versus 403. Sanctum versus policies. Add: for a first-party SPA use cookie-based auth, not tokens, because a stored token is exposed to XSS.

4 · How do you add a POST endpoint?

Migration → model → Form Request → controller → Resource → route. Add: 422 comes free from the Form Request; $fillable guards mass assignment.

5 · Do you write tests? What do you test?

Feature tests, because they cover the whole stack. Happy path plus the failures — 401, 403, 422, 404. RefreshDatabase for isolation, factories for data. Add: "I test the failure paths, not just the happy path."

6 · Where does business logic belong?

Not the controller. Service layer when logic is shared or complex. Add the judgement: for simple CRUD a service is indirection without benefit.

7 · Explain middleware.

Runs before the controller and can reject the request — auth, rate limiting, CSRF, tenant resolution. Add: it is why a controller can assume a valid user exists.

8 · What is a migration, and why not just edit the database?

Version-controlled, executable schema. Every environment and teammate gets the same structure, and changes are reviewable in a PR. Add: in Laravel 11+, ->change() drops modifiers you do not re-state — a real upgrade hazard.

9 · When do you need a transaction?

When one logical operation spans several writes and a half-finished state would be wrong. Add: jobs dispatched inside a transaction can run before it commits — hence after_commit.

10 · Tell me about multi-tenancy. (your differentiator)

See section 3 — this one needs care.

3Your strongest story, told honestly

Multi-tenancy is the most distinctive thing you can discuss. It is also where you could overclaim and get caught. Here is the calibration:

Say this

"The product I worked on was a multi-tenant SaaS — one Laravel API serving many organisations. I worked on the frontend, but I spent time reading the backend because I wanted to move into full-stack work. It used single-database tenancy: one shared database, a tenant_id column, and a global Eloquent scope that appends the tenant filter to every query automatically.

The part I found most interesting is that the scope is a no-op when tenancy isn't initialised — so in a queue job or an admin panel, the same query silently returns every tenant's rows. Their repositories handle it by dropping the scope deliberately and replacing it with an explicit tenant constraint that fails closed: an empty tenant list matches nothing rather than everything."

Not this

"I built a multi-tenant system." You did not, and two follow-up questions will establish that. The honest version is more impressive, because "I read production code carefully and understood a subtle failure mode" is exactly the behaviour that makes someone useful in week one.

The same applies throughout: "I've read" and "I've built" are different claims, and the first is still valuable. Interviewers trust candidates who draw that line themselves.

4Take-home strategy

Take-homes are where you can outperform your experience level, because they reward care rather than speed.

DoWhy it works
Write a READMESetup steps, decisions, known trade-offs. Many submissions have none; yours will stand out before any code is read.
Include testsThe single biggest differentiator. Even four.

And the inverse: do not gold-plate. A clean, tested, well-explained small solution beats a sprawling one with half-finished extras.

5Answering what you do not know

This will happen, and how you handle it is itself being assessed.

Say what you do know, then the boundary

"I haven't used queues in production. I understand the idea — push slow work to a background worker so the request returns fast — and I've seen jobs in a codebase that used Horizon, but I haven't written one myself." Honest, demonstrates partial knowledge, and invites them to teach you — which interviewers enjoy.

Never bluff

Experienced interviewers detect it instantly, and it poisons the answers they believed before it. One admitted gap costs little; one caught bluff costs the interview.

Reach for a real parallel

Four years of frontend gives you genuine ones: N+1 is fetch() in a .map(); middleware is a navigation guard; DI is provide/inject. Showing you can map new concepts onto known ones is a sign you will learn their codebase quickly.

6Final retrieval

An interviewer asks about something you have never used. Best response?

What most improves a take-home submission?

The final exercise. Record yourself answering: "Tell me about your experience with Laravel." Two minutes. Then listen back.

A strong two minutes covers: where you come from (four years frontend, Vue primary) · why Laravel (worked against a production Laravel API, wanted to move full-stack) · what you know (lifecycle, Eloquent and N+1, validation, Sanctum and policies, feature tests) · your distinctive bit (read a multi-tenant codebase, understood its scoping model and failure modes) · honest edges (not yet used queues in production).

Listen for: filler words, trailing off, apologising for your experience. Say "I'm moving into backend" rather than "I'm only a frontend developer." The facts are identical; one of them is accurate about your trajectory.

7What comes after this course

Ten lessons end here. Honestly, that is enough to interview with — and not enough to stop. In priority order:

1 · Build one public thing

You deferred this, reasonably. Reconsider now: without a merged PR at your old job, a small, tested, well-documented API on GitHub is the only evidence a hiring manager can inspect directly. A halaqa-shaped app would be ideal — you know the domain cold, and that shows in the modelling. Two weekends, and worth more than two more lessons.

2 · Join one community

Laracasts Discuss · Laravel Discord · r/laravel. Answering a beginner's question is retrieval practice with social stakes — it exposes gaps faster than reading does.

3 · Learn queues when you need them

Deliberately cut from this course. Worth a weekend once the fundamentals are solid — it is the most common "we also use…" in Laravel postings.

4 · Keep using me

Bring real take-home tests, real interview questions you fumbled, real code for review. That is more useful now than more lessons.

Primary source — ongoing

The Laravel 12.x documentation, as a reference rather than a book. You now know enough vocabulary to find things in it quickly, which is the real skill.

For interview breadth: Laravel News keeps you current on what teams are discussing.

Ask your teacher — this is where I become most useful

"Run a mock interview. Ask me ten questions, grade each answer." · "Here's a take-home I received — help me plan it." · "Here's the code I submitted. What would a reviewer say?" · "I was asked X and froze. What should I have said?" · "Here's a job posting — am I a realistic candidate?"

The mock interview is the highest-value thing I can do for you now. Ask for it before your first real one, not after.

Lesson 10 of 10 — course complete. Good luck. You know more than you think you do; the task now is saying it clearly.
