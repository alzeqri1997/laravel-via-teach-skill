Lesson 01 · Laravel Foundations

What Happens Before Your fetch() Resolves

You have spent four years calling endpoints. Today you learn what is on the other end of the wire — the seven steps between a URL and a response.

Laravel 13.x · ~20 minutes · Prerequisite: none

Why this lesson first

Every Laravel concept you will ever learn — middleware, controllers, Eloquent, validation, tenant scoping — is a stop on this one path. Learn the path and each new concept becomes "ah, that's the fourth step," rather than another disconnected term. Skip it and you will be memorising vocabulary forever.

1The thing you already know, from the other side

When you write this in Vue:

HalaqaList.vue

const res  = await fetch('/api/halaqas/42')
const data = await res.json()

…you think of the server as a black box that takes a URL and returns JSON. That box is not mysterious. It is a pipeline with seven stages, and in Laravel every stage is a file you can open and read.

Here is the whole thing. Do not memorise it yet — just look at the shape:

  ①  Browser sends    GET /halaqas/42
        ↓
  ②  public/index.php     ← the ONLY entry point. Every request. No exceptions.
        ↓
  ③  Bootstrap            ← framework wakes up, reads .env, loads config
        ↓
  ④  Router               ← "which code handles /halaqas/42?"   routes/web.php
        ↓
  ⑤  Middleware           ← gatekeepers: logged in? CSRF ok? which tenant?
        ↓
  ⑥  Controller           ← YOUR code. Asks the model for data.
        ↓         ↕
        ↓      Model / Database   ← Eloquent builds SQL, runs it
        ↓
  ⑦  Response             ← Blade page or JSON, sent back to the browser
        ↓
     Your await resolves.
The one that surprises frontend developers

Stage ② is the shock. In a Vue SPA your app boots once and lives in memory while the user clicks around. In PHP, the entire application boots, handles one request, and dies — then boots again from scratch for the next one. There is no long-lived memory between requests. This is why Laravel has sessions, caches, and databases: they are how state survives a process that is constantly being destroyed.

2Your frontend knowledge, translated

You are not starting from zero. You already own the concepts — under different names:

You know thisLaravel calls itWhere the analogy breaks
Vue Router routes routes/web.php Runs on the server before any HTML exists. Matching happens once, then the process dies.
Navigation guards Middleware Genuinely enforces security. A client guard is a suggestion; middleware is the real lock.
Component <template> Blade view Rendered to a string on the server and shipped as text. No reactivity, no re-render.
API client / composable Eloquent model Talks straight to the database. No network hop, so a sloppy loop costs you real queries.
TypeScript interface Migration Actually creates the tables. It is executable schema, not a compile-time promise.
Zod / form validation Form Request Server-side, so users cannot bypass it with devtools. Yours is UX; this is truth.
The theme worth internalising

Notice the pattern in that last column. Almost every frontend equivalent is advisory — a user with devtools can defeat it. The server-side version is authoritative. This is the single biggest mental shift in moving to backend work: your code stops being a helpful suggestion and becomes the thing that actually decides.

3Reading a real route

Here is roughly what a route in your halaqa codebase looks like. Four lines, and every stage from section 1 is visible in it:

routes/web.php

Route::get('/halaqas/{halaqa}', [HalaqaController::class, 'show'])
    ->middleware(['auth', 'tenant'])
    ->name('halaqas.show');

Read left to right, it says:

  • Route::get — when a GET request arrives (stage ④)
  • /halaqas/{halaqa} — matching this URL, where {halaqa} is a wildcard captured as a parameter
  • [HalaqaController::class, 'show'] — run the show method on HalaqaController (stage ⑥)
  • ->middleware(['auth', 'tenant']) — but first, pass through two gatekeepers: is this user logged in, and which tenant do they belong to (stage ⑤)
  • ->name('halaqas.show') — a nickname, so other code can build this URL without hardcoding the string
Mission-critical: that tenant middleware

Your work application is multi-tenant — one codebase serving many separate organizations, each seeing only its own halaqas. That 'tenant' middleware is what establishes "who is asking" before any of your code runs. Almost every serious bug in a multi-tenant app is data leaking between tenants because something ran outside that boundary. You do not need to understand the mechanism yet. You need to know it exists, and treat it with respect.

4Retrieval practice

Answer from memory before scrolling back. Getting one wrong and correcting it builds more durable memory than getting it right easily — that is the point of the difficulty.

A user loads two pages in a row. What happens to the Laravel application between the first response and the second request?

A logged-out user requests /halaqas/42, which requires authentication. Which stage stops them?

Without looking: name as many of the seven stages as you can, in order, from browser to response.

1. Browser sends request  2. public/index.php entry point  3. Bootstrap  4. Router  5. Middleware  6. Controller (↔ Model ↔ Database)  7. Response

Got 5 or more in roughly the right order? That is a pass — this comes back in later lessons, and spaced repetition is what will actually cement it. Fewer than 5? Re-read section 1 once, then try again tomorrow rather than right now. The gap is what does the work.
