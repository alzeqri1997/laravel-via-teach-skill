Lesson 02 · Laravel Foundations

Reading the Endpoint You Used to Call

Your codebase is a JSON API. Today you learn to read one endpoint from URL to response — and to name the four files any endpoint lives in.

Laravel 13.x · ~25 minutes · Prerequisite: Lesson 1

What changed since Lesson 1

You confirmed your work codebase is API-only: Laravel returns JSON, and the frontend is a separate SPA. That is good news. There is no Blade templating layer to learn, and the boundary you already work against every day — the JSON contract — is now the thing you will be editing from the inside. Everything you know about consuming an API becomes knowledge about building one.

1Cold recall first

Before any new material. This was Lesson 1, and the gap since then is exactly what makes retrieving it valuable — struggling to recall is the mechanism, not a sign of failure.

A request hits your Laravel API. Name the stages it passes through, in order. Then: which stage rejects a request carrying an expired token?

Stages: browser → public/index.php → bootstrap → router → middleware → controller (↔ model ↔ database) → response.

Expired token: middleware — before your controller runs at all. This is why an endpoint's controller can assume a valid user exists: something upstream already guaranteed it. In an API codebase that middleware is usually auth:sanctum rather than auth.

2The four files behind one endpoint

When your SPA calls GET /api/halaqas/42, four files on the server cooperate to answer it. Learning to find these four is the skill of reading a Laravel API:

FileIts jobWhat you ask it
routes/api.php The switchboard Which controller handles this URL?
app/Http/Controllers/ The handler What actually happens on this request?
app/Models/ The data access What is a Halaqa, and what relates to it?
app/Http/Resources/ The JSON shape Which fields actually reach the frontend?
The one to notice

That fourth file is the one that will surprise you, and it is the most useful to your daily work. When the SPA team says "the API isn't returning teacher_name", the answer is almost never in the controller. It is in the Resource — the translation layer deciding which model fields become JSON. Knowing that one fact makes you immediately useful on backend tickets.

3Tracing one endpoint, file by file

Here is a realistic halaqa endpoint. Read the files in order — this is exactly the sequence you will follow in a real codebase.

① The route — where you always start

routes/api.php

Route::middleware(['auth:sanctum', 'tenant'])->group(function () {
    Route::apiResource('halaqas', HalaqaController::class);
});

Two lines, a lot of meaning. apiResource is a shorthand that registers five routes at once — the CRUD set, minus the two that would only serve HTML forms (docs):

VerbURIController method
GET/api/halaqasindex — list them
POST/api/halaqasstore — create one
GET/api/halaqas/{halaqa}show — fetch one
PUT/PATCH/api/halaqas/{halaqa}update — change one
DELETE/api/halaqas/{halaqa}destroy — remove one
Why this matters when reading unfamiliar code

You will search the codebase for halaqas/42 and find nothing, because that URL is never written down anywhere. It is generated by that one apiResource line. This is the most common way newcomers get lost in a Laravel repo. The fix is a command: php artisan route:list --path=halaqa prints every real route, fully expanded — the authoritative answer to "what endpoints exist?"

② The controller — the handler itself

app/Http/Controllers/HalaqaController.php

<?php

namespace App\Http\Controllers;

use App\Http\Resources\HalaqaResource;
use App\Models\Halaqa;

class HalaqaController extends Controller
{
    public function show(Halaqa $halaqa)
    {
        return new HalaqaResource($halaqa);
    }
}

That is a complete, production-shaped endpoint. Read the signature closely — it contains the most magical line in Laravel:

public function show(

The method name matches the table above: show handles GET /api/halaqas/{halaqa}. Wired by convention, not configuration.

Halaqa $halaqa

Route model binding. Because the parameter is type-hinted as the Halaqa model and the variable name $halaqa matches the {halaqa} URI segment, Laravel runs the database lookup for you. By the time your code executes, $halaqa is a loaded model. If no row matches, Laravel returns 404 automatically and your method never runs (docs).

return new HalaqaResource($halaqa)

Hand the model to the Resource, which decides the JSON shape. No json_encode, no status code, no headers — returning a Resource is enough.

The habit that will save you

Notice what is absent: no null check, no "is this user allowed" check, no tenant check. A thin controller is idiomatic Laravel — those checks live in middleware and in model binding. But it means you cannot judge an endpoint's security by reading its controller alone. You must read the route's middleware too. When you review backend code, always read the route first.

③ The model — what a Halaqa is

app/Models/Halaqa.php

class Halaqa extends Model
{
    protected $fillable = ['name', 'teacher_id', 'schedule'];

    public function students()
    {
        return $this->hasMany(Student::class);
    }

    public function teacher()
    {
        return $this->belongsTo(User::class, 'teacher_id');
    }
}

Take two things from this file for now. $fillable lists which fields may be set from user input — a safety list. And the methods below it declare relationships: a halaqa has many students and belongs to a teacher. Those become $halaqa->students and $halaqa->teacher elsewhere in the code. Relationships get a full lesson of their own; today you only need to recognise them on sight.

④ The resource — the JSON contract

app/Http/Resources/HalaqaResource.php

class HalaqaResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        return [
            'id'            => $this->id,
            'name'          => $this->name,
            'teacher_name'  => $this->teacher->name,
            'student_count' => $this->students->count(),
        ];
    }
}

This is the file your SPA actually consumes. Whatever sits in that array is what the frontend receives — and, just as importantly, whatever is not in it stays on the server. The halaqa row might have fifteen columns; the API exposes four.

The response your fetch() resolves with:

{
  "data": {
    "id": 42,
    "name": "Halaqa Al-Noor",
    "teacher_name": "Ustadh Kareem",
    "student_count": 12
  }
}
That data wrapper

Laravel wraps the outermost resource in a data key by default — which is why SPA code so often ends up reading res.data.data. It can be switched off globally with JsonResource::withoutWrapping() in a service provider (docs). If your codebase's responses are not wrapped, that call is the reason — worth searching for.

4The trace, end to end

SPA:  fetch('/api/halaqas/42')
        ↓
routes/api.php          apiResource → HalaqaController@show
        ↓
middleware              auth:sanctum ✓   tenant ✓       ← fails here = 401
        ↓
route model binding     SELECT * FROM halaqas WHERE id = 42   ← no row = 404
        ↓
HalaqaController@show   receives $halaqa, already loaded
        ↓
HalaqaResource          picks 4 fields out of the model
        ↓
JSON  { "data": { ... } }   → your await resolves

Four files, one path. Every endpoint in your work codebase follows this shape. When you are handed a ticket, this is your reading order: route → middleware → controller → model → resource.
