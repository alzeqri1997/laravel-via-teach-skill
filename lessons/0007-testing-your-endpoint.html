Lesson 07 · Laravel 12

The Test That Gets You Hired

Most candidates at your level cannot write a test. A take-home with tests is reviewed differently from one without — this is the highest-leverage lesson here.

Laravel 12 · ~35 minutes · Prerequisite: Lesson 6

Why this lesson matters more than the others

A take-home submission with a handful of passing feature tests reads as "this person has worked on a team". Without them it reads as "this person has done tutorials" — regardless of how good the code is.

You do not need deep testing theory. You need to write one good feature test and explain why it is worth having. That is a weekend's work and it moves you ahead of a lot of the field.

1Cold recall

From Lesson 6: which layer produces 401, which produces 403, and which produces 422? Name the mechanism behind each.

401 — authentication. auth:sanctum middleware: no valid token or session cookie.
403 — authorization. A policy or gate returned false.
422 — validation. Form Request rules() failed.

Today you write tests that assert exactly these three, which is also how you will remember them.

2Two kinds of test, and which to write

KindTestsUse it when
Feature A real HTTP request through the whole stack Almost always. Highest confidence per line written
Unit One class or method in isolation Tricky pure logic — a calculation, a parser
Say this if asked "unit or integration?"

For a Laravel API, feature tests give far more confidence per unit of effort, because they exercise routing, middleware, validation, the controller and the database together — the places bugs actually live. Unit tests are for isolated logic worth pinning down separately.

That answer is practical rather than dogmatic, which is what experienced interviewers want to hear.

3A complete feature test

tests/Feature/ProgressTest.php

<?php

namespace Tests\Feature;

use App\Models\Progress;
use App\Models\User;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Laravel\Sanctum\Sanctum;
use Tests\TestCase;

class ProgressTest extends TestCase
{
    use RefreshDatabase;

    public function test_a_teacher_can_record_progress(): void
    {
        Sanctum::actingAs(User::factory()->create());

        $response = $this->postJson('/api/progress', [
            'student_id'  => 1,
            'pages'       => 5,
            'recorded_on' => '2026-10-18',
        ]);

        $response->assertStatus(201)
                 ->assertJsonPath('data.pages', 5);

        $this->assertDatabaseHas('progress', ['pages' => 5]);
    }
}

Every line earns its place:

use RefreshDatabase;

Each test runs inside a transaction that is rolled back afterwards. Tests never see each other's data and never leave rows behind. Without this, tests pass alone and fail together — a classic beginner symptom.

Sanctum::actingAs(User::factory()->create())

Authenticate without logging in. factory() builds a valid User with fake data — no fixtures, no seeded database. Add abilities with a second argument: actingAs($user, ['view-tasks']).

$this->postJson(...)

A real request through routing, middleware, validation and the controller. Use getJson, putJson, deleteJson likewise — the JSON variants set the right headers so you get JSON errors rather than redirects.

assertStatus(201)->assertJsonPath(...)

Assert the contract: status code, then shape. assertJson checks a fragment — extra keys still pass — while assertExactJson demands a complete match.

assertDatabaseHas(...)

The response said it worked; this proves it persisted. A response can lie — this is the assertion that catches a controller which returns 201 without saving.

4The four tests worth writing

For any endpoint, these four cover the ground an interviewer cares about:

public function test_it_requires_authentication(): void
{
    $this->postJson('/api/progress', [])->assertStatus(401);
}

public function test_it_validates_the_payload(): void
{
    Sanctum::actingAs(User::factory()->create());

    $this->postJson('/api/progress', ['pages' => 'not-a-number'])
         ->assertStatus(422)
         ->assertJsonValidationErrors(['pages', 'student_id', 'recorded_on']);
}

public function test_it_forbids_editing_another_users_record(): void
{
    Sanctum::actingAs(User::factory()->create());
    $other = Progress::factory()->create();   // belongs to someone else

    $this->putJson("/api/progress/{$other->id}", ['pages' => 9])
         ->assertStatus(403);
}

public function test_it_returns_404_for_a_missing_record(): void
{
    Sanctum::actingAs(User::factory()->create());

    $this->getJson('/api/progress/99999')->assertStatus(404);
}
Test the unhappy paths — that is the signal

Beginners test that things work. Experienced developers test that things fail correctly. Those four tests prove your auth, validation, authorization and binding all behave — which is precisely what a reviewer wants to know, and precisely what a tutorial follower never writes.

Note assertJsonValidationErrors: it asserts specific fields failed, so the test still catches a regression if you later change the error wording.

5Factories

Tests need data. Factories generate it (database/factories/):

class ProgressFactory extends Factory
{
    public function definition(): array
    {
        return [
            'student_id'  => Student::factory(),
            'pages'       => fake()->numberBetween(1, 20),
            'recorded_on' => fake()->date(),
        ];
    }
}
Progress::factory()->create();                      // one, saved
Progress::factory()->count(10)->create();           // ten
Progress::factory()->create(['pages' => 5]);        // override a field
Progress::factory()->make();                        // built, NOT saved

'student_id' => Student::factory() creates the parent automatically — nested factories mean a test needs one line to produce a whole valid object graph.

6Running them

php artisan test                              # all
php artisan test --filter=ProgressTest        # one class
php artisan test tests/Feature/ProgressTest.php
php artisan test --parallel                   # faster

Ethaaf uses ./vendor/bin/phpunit with Unit, Feature and Architecture suites. That third one enforces structural rules — "controllers must not call the database directly", for instance. Mentioning you have seen architecture tests is a small, credible differentiator.

7Retrieval practice

What does the RefreshDatabase trait give you?

Why add assertDatabaseHas when you already asserted a 201?

For a Laravel API, why do feature tests usually beat unit tests?

Out loud: "What would you test on an endpoint that creates a record?" Name the cases before you look.

Happy path — valid payload, authenticated user → 201, correct JSON, assertDatabaseHas.
Unauthenticated → 401.
Invalid payload → 422 with assertJsonValidationErrors.
Forbidden — authenticated but not permitted → 403.
Missing related record → 404.

Then, if the endpoint has them: edge cases around boundaries (zero, maximum, past dates) and any business rule the Form Request enforces.

Saying "I'd test the failure paths, not just the happy path" is the sentence that makes a reviewer relax.

8Version shift

12 ← 10 · Ethaaf

Everything here works in Laravel 10. The differences are cosmetic: Laravel 11+ ships Pest as the default test runner (docs show both Pest and PHPUnit tabs), while Ethaaf uses classic PHPUnit classes. Pest's test('name', function () { … }) is the same engine with different syntax — read either comfortably.

9Your task before Lesson 8

One — write four tests. In your practice app, write exactly the four from section 4 against the endpoint you built in Lessons 5–6. Watch them fail first (comment out the middleware, see the 401 test break), then pass. Seeing a test fail for the right reason is how you learn to trust it.

Two — read one of Ethaaf's. Open any file in C:/laragon/www/ethaaf/tests/Feature/ and read it. Production tests are messier than tutorial ones; getting used to that is valuable.

Three — out loud. "Do you write tests? What do you test?" in under a minute. This question is nearly certain to come up.
