2Sanctum's two modes

ModeForMechanism
API tokensMobile, third-party, scriptsAuthorization: Bearer …
SPA authYour own frontendSession cookies + CSRF

Docs: "You should not use API tokens to authenticate your own first-party SPA." Cookies give CSRF protection and keep credentials out of JavaScript (XSS).

Token operations

// Issue
$user->createToken('device-name')->plainTextToken;          // plain text ONCE
$user->createToken('name', ['server:update'])->plainTextToken;  // with abilities

// Check an ability
$user->tokenCan('server:update');

// Revoke
$user->tokens()->delete();                           // all
$request->user()->currentAccessToken()->delete();    // this one = logout
$user->tokens()->where('id', $id)->delete();         // specific

// Protect
Route::get('/user', fn (Request $r) => $r->user())->middleware('auth:sanctum');

Requires use Laravel\Sanctum\HasApiTokens; on the User model. Tokens are stored SHA-256 hashed and never expire unless config/sanctum.php's expiration is set.

3Policies

php artisan make:policy ProgressPolicy --model=Progress
class ProgressPolicy
{
    public function before(User $user, string $ability): bool|null
    {
        return $user->isAdministrator() ? true : null;   // null = fall through
    }

    public function viewAny(User $user): bool { … }       // no model
    public function view(User $user, Progress $p): bool { … }
    public function create(User $user): bool { … }        // no model
    public function update(User $user, Progress $p): bool { … }
    public function delete(User $user, Progress $p): bool { … }
}

Auto-discovered — Progress → ProgressPolicy in app/Policies/. No registration.

Invoking itBehaviour
Gate::authorize('update', $p)Throws → 403
$user->can('update', $p)Boolean
$user->can('create', Progress::class)Boolean, no instance
->can('update', 'progress') on a routeMiddleware → 403
In a Form Request's authorize()→ 403

Gates vs policies: policies group rules around a model; gates are standalone closures for model-less abilities (viewing an admin dashboard). Define gates in AppServiceProvider::boot() with Gate::define(...).

Useful detail

Response::denyAsNotFound() returns 404 instead of 403 — hides a record's existence from someone not allowed to see it.

4Feature test skeleton

class ProgressTest extends TestCase
{
    use RefreshDatabase;

    public function test_a_teacher_can_record_progress(): void
    {
        Sanctum::actingAs(User::factory()->create());

        $this->postJson('/api/progress', ['pages' => 5])
             ->assertStatus(201)
             ->assertJsonPath('data.pages', 5);

        $this->assertDatabaseHas('progress', ['pages' => 5]);
    }
}

5Interview answers

"401 vs 403?"

401 — we don't know who you are; log in. 403 — we know, and you still may not.

"How do you log out of a token API?"

Delete the token: currentAccessToken()->delete(). There is no session.

"Tokens or cookies for your SPA?"

Cookies — CSRF protection, and no token sitting in JavaScript for XSS to steal.

"Do you write tests?"

Feature tests covering the whole stack: happy path plus 401, 403, 422, 404. RefreshDatabase for isolation, factories for data. "I test the failure paths."

6Version notes

12 ← 10 · Ethaaf

Concepts identical. Ethaaf uses Sanctum 3.x (Laravel 11+ requires 4.x — a high-impact upgrade), has no install:api command, and uses PHPUnit classes rather than Pest. It also layers spatie/laravel-permission on top for named permissions.

12 → 13

Laravel 13 adds an #[Authorize] controller attribute. In 12, use Gate::authorize() or ->can() on the route.
